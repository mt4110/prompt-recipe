# 実装計画とレビュー事項

状態：2026-10-04の提案。設計後に初期実装のGoを受け、作業開始。現在の実装はdocs/IMPLEMENTATION.mdを参照。公開・配布・オンライン通信・有料検証は未承認。

## 段階

| 段階 | 成果物 | 確認すること |
| --- | --- | --- |
| D0 設計レビュー | 製品・教材・技術設計、操作案 | 通常画面と小窓の役割、教材の目的、初期範囲 |
| D1 最小の実例検証 | L01/L03/L05の合成課題と成果物、固定した開始状態 | 過去の個人ログなしで使えるか、余計な工程を増やさないか |
| D2 操作の基盤 | macOSの小窓・IME・コピー・復帰、手動登録 | 日常の呼出しが成立するか。ここで技術選択を再判定 |
| D3 初期利用版 | 版、セット、割り当て、変数、ローカル衝突検査、Export | プロジェクトに適用し、案件情報を混ぜずに再利用できるか |
| D4 学習と改善 | 教材詳細、版付き報告、手動改善、差分採用、教材パック更新 | 利用者の理解とレシピの改善がつながるか |
| D5 公開候補 | 権利、再現済み教材、導入／復旧、配布資料 | 誇大な効果主張がなく、説明と実態が一致するか |
| D6 拡張 | Services、CLI指示書更新、他OS、任意通信 | 実利用の負担が大きい部分から追加する |

D3だけを完成版として公開しない。衝突検査、フィードバックと改善、教材更新を備えたD4までを最初の利用版の契約とする。
D1の実行は隔離した合成データから始める。有料モデル、特権操作、外部通知・デプロイは対象・予算・承認を別途決める。
L08の既存公開記録は実例設計に使えるが、Prompt Recipeによる改善の証拠とは扱わない。

## 価値の確認

利用者自身の実依頼について、従来のメモ／手入力と比較する。開始状態、成功条件、利用環境、取得範囲を揃える。
見るのは準備の手間、文面の手直し、前提の再説明、逸脱の訂正、完了までの時間、品質、取得できる資源量。
コピー成功数を問題解決数としない。学習は「別の課題へ適用理由を説明できるか」で任意に確認し、自己評価だけを成果証明にしない。
初回の環境整備・教材学習にかかった費用と、その後の利用費用を別に示す。節約が成立するかは合計で判断する。

## 継続・中止条件

- 必須の安全性・入力保全・版復旧・案件情報分離が成立しない場合は、その経路の公開を止める。
- 説明し直しや手直しが減らず、管理の手間だけ増える場合は、セット構造とUXを簡素化して再確認する。
- 技術的に動いても普段使われない場合は機能追加で補わず、入口と具体的用途を見直す。
- 規模の小さい課題で重い設計／多エージェントを要求する教材は短縮・分離・非推奨を検討する。
- 教材更新の維持費が主力プロダクトを圧迫する場合は範囲を絞る。確認できない教材数を増やさない。
- 比較可能な資源データが取れなければ、節約率を公開せず、確認できた操作負担の結果だけ示す。

数値の合格基準は観測前に便宜的に作らない。実利用の基準と予算を決め、明確な失敗を同じ手順で繰り返さない。

## 先にレビューしたい判断

1. 教材を「実例 → 指示 → 理由・検証」で見せ、普段は短い指示だけ使う構成。
2. 初期ネットワークなし＋教材パックの手動更新。更新を継続するのは教材運用の責務。
3. 自分用の版と案件への割り当てを固定し、更新は差分を見て採用する構成。
4. 最初の実例は理解確認・最小ハーネス・並列設計に絞り、全領域の深い教材は順次検証する構成。

実装前に決める項目：macOSの最低対応版、初期教材の公開範囲、ライセンス、保存場所と保管期限、配布経路、実例検証の予算。
初稿ではこれらを既決事項と扱わない。収益化の形も未決定で、OSS公開の希望から公開・配布を自動実行しない。

## V0.1の到達点（2026-10-08）

自己利用へ進める機能：台帳、Gitルートの選択、名前付きセット、JSON移行、大小切替、XML／Markdown基本Lint。最終ビルドと限定macOS確認はIMPLEMENTATION.mdに記録する。

残る受け入れ：初見の利用者、IME／VoiceOver、CPU・メモリ・IPC・電力測定、教材の実例再現。ZIPは安全設計と検査エンジン判断、署名・公証・Windows／CLI配布、オンライン更新は方式・費用・権限判断後。機能を増やす前に、自分の台帳登録・検索・再利用が日常で使われるかを確認する。
