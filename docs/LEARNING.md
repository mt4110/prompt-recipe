# 教材と継続改善

状態：レビュー用初稿 / 2026-10-04。以下のレシピは教材の設計候補。効果検証済みの組み込みカタログではない。

## 1. 学習の契約

使う → 適用理由を知る → 結果を確かめる → 自分の案件に置き換える、を一つの教材で支える。
プロンプトの文言を暗記させず、課題の分解・境界・資源・検証・人の判断を学ぶ。
教材には長く残る原則と、モデル／ツール／環境に合わせて変える具体的手順を分けて持たせる。

## 2. 分類

領域：ソフトウェア基礎、インフラ、k8s、並列設計（RunAlways仮称）、アーキテクチャ／全体システム、低レイヤー。
難易度は領域と独立し、前提知識・変更権限・失敗時の影響から設定する。

探し方には、日常の依頼（分析・修正・設計・相談）と、達成したい目的（品質・時間・コスト・理解）を追加する方針を合意した。同じレシピへ複数の分類を付けられるようにし、領域・難易度・目的を一つの階層へ押し込めない。目的は任意の絞り込みで、選択を必須にしない。
2026-10-08時点でactions/goals属性、共通UIフィルター、SQLite保存とJSON Importに実装済み。分類省略の旧形式も受け付け、未知・重複分類は拒否する。教材の説明文である「目的」と、検索用の目的分類は区別する。操作の詳細は `docs/PRODUCT.md` の「日常の依頼と目的から探す」を参照する。

| 難易度 | 前提と学ぶこと | 代表課題 |
| --- | --- | --- |
| 初級 | ファイルと差分が読める。依頼の範囲と完了条件 | 小さなバグの再現、理解確認、レビュー境界 |
| 中級 | テスト・依存・実行環境が扱える | 有界の検証ハーネス、キャッシュ条件、ローカルk8s診断 |
| 上級 | 複数サービス・状態・運用の関係が分かる | 並列分担、障害復帰、権限、全体設計 |
| 超上級 | OS境界・寿命・特権・実験復旧を扱える | eBPF／ABI／カーネルの実験設計と実環境検証 |

難易度を権限や能力の保証とせず、教材ごとに必要な知識と実行条件を示す。教材数で全分類を埋めることを目標にしない。

## 3. 教材の共通構造

必須：目的、困った場面、具体例の入力と成果物、レシピ本文、入力定義、適用条件、確認手順、失敗例・限界、出典・権利、更新履歴。
追加：構造化制約、必要能力、環境の版、再現手順、比較対象、実測記録、費用、復旧手順。
「なぜこの指示か」は短い説明から読め、詳細は必要なときに開く。教材解説はコピー本文へ既定で含めない。
個人の短い指示はこの全構造を要求しない。組み込み教材の公開基準として用いる。

## 4. 実例と証拠

| 状態 | 表示できること |
| --- | --- |
| 構想 | 課題と想定手順。効果は仮説 |
| 出典確認 | 元資料と確認範囲。再実行していない |
| 再現済み | 固定した環境・手順で得た成果物と結果 |
| 比較済み | 比較条件・費用・品質・複数実行のばらつきを含む結果 |
| 再検証待ち | 原因、最終確認日、使える条件と未確認条件 |
| 非推奨 | 理由、移行先、旧版の閲覧／Export |

技術的な動作の証拠と、そのレシピが結果を改善した証拠を別にする。リポジトリにハーネスがあるだけで、プロンプトによる改善と結論しない。
測定は同じ課題・開始状態・成功条件を使い、モデル、推論設定、ツール、権限、キャッシュ状態、再試行を記録する。
使用量は取得できる入力・キャッシュ入力（入力の内数）・出力を区別する。未取得をゼロにしない。プロバイダー間で取得範囲が違えば単純比較しない。
削減は検証・品質を弱めず、統合やレビューの負担を含めて評価する。電力・電気代へ架空の換算をしない。

## 5. 最初の代表レシピ

### L01 着手前の理解確認 / 初級

場面：正本を渡したが、今回の変更に適用できているか不明。
成果物：目的・非変更範囲・制約・配置・不明点の短い対応表。

> まだ設計・実装に着手せず、指定した指示書と正本を読んでください。参照先と、今回の目的・変更しない範囲・関連制約・変更を置く場所と理由・不明点を、自分の言葉で簡潔に示してください。読めない資料はその旨を示してください。要約だけで終わらず今回の依頼との対応を示し、私の確認を待ってください。

確認：制約の列挙ではなく変更への適用があるか。誤解を含む合成課題で着手前に発見できるか。
限界：正しい説明は実装の遵守を保証しない。ファイル参照不可なら利用者の抜粋が必要。

### L02 モデルと資源を選ぶ / 初級〜中級

場面：小さな保守に重い設定を使う、長い読込を始めてから費用に気付く。
成果物：確認できた候補、必要範囲、概算の幅と仮定、削減方法、停止点。

> 依頼の難易度・不確実性・影響範囲を判断し、利用可能と確認できるモデル／推論設定から必要十分な候補を原則二つ以内で提案してください。着手前に、作業範囲、読込・再試行を含めた使用量の概算と仮定、減らせる工程と品質への影響を示してください。利用不能な切替や未取得の数値を実施済み・実測と扱わず、私の選択を待ってください。

確認：見積もりを実測と区別し、実際の使用量と差を振り返る。単純な作業へ長い選定工程を持ち込まない。
限界：プロンプトだけでモデル切替や予算制御はできない。利用環境の機能が必要。

### L03 検証ハーネスを最小で整える / 中級

場面：同じ問題で毎回環境調査と検証コマンドを探している。
成果物案：適用範囲の指示書、入口一つの検証コマンド、失敗が分かる結果、変更に応じた読込案内。

> 現在の失敗を一つ再現し、既存の検証入口を確認してください。再現・修正・回帰確認を繰り返せる最小のハーネスを設計してください。依存追加なしの案を先に検討し、成功／失敗条件、タイムアウト、終了コード、ログに含めない情報を明示してください。関係のない変更で全検証を要求せず、必要な確認を対応付けてください。設計と概算費用を示したところで確認を待ってください。

確認：わざと壊した代表ケースで失敗を検出し、修正後に回帰が通るか。新しい会話から入口を発見できるか。
限界：ハーネス追加の維持費もある。初回の整備費と後続作業の費用を分けて評価する。

### L04 キャッシュとデータストアを判断する / 中級

場面：調査・検証結果を再利用したいが、古い情報を正本として扱いたくない。

> 再利用したい処理と入力を特定し、キャッシュを設けない案と比較してください。キーに必要な入力・コード・環境の版、無効化条件、期限、容量、所有者を定義してください。元データ、キャッシュ、意思決定記録を区別し、秘密情報や案件外への持出しを避けてください。期限切れ・破損・未確認を成功と扱わず、最小の検証方法を示してください。

成果物：入力hash＋環境版のキー設計、再計算条件、保存方針、変更時に再利用を拒否するテスト案。
限界：AIサービス側のプロンプトキャッシュと、プロジェクト内の成果物キャッシュは別。ヒット率を根拠なしに示さない。

### L05 並列設計 / 上級

場面：独立調査は並列にしたいが、重複と統合で費用が増える。

> 目的と成功条件を共有し、依存する仕事と独立する仕事を分けてください。担当範囲、必要な情報、成果物形式、統合担当、競合時の扱いを定義してください。重複調査・同じファイルの同時編集を避け、スキルは品質か総費用に利点がある場合に使ってください。単独で進める案との費用・待ち時間・レビュー負担を比較し、予算と終了条件を守ってください。

成果物：契約／テスト／調査などの独立分担と統合計画。速度だけでなく品質と総費用を確認する。
限界：並列化が常に安い・速いとは限らず、利用環境での実行可否を確認する。

### L06 全体システム設計 / 上級

場面：コードの構造だけでなく、運用・権限・障害復帰も含めて設計したい。

> 目的と非対象を確認し、データの流れ、責務、信頼境界、保存と削除、権限、失敗時の状態、復旧手順を設計してください。既存機能と実装しない案を比較し、正本へ対応付けてください。AIが検証できる項目と、人が決める製品・運用・公開判断を分け、実装／デプロイ前に必要な判断事項を示してください。

成果物：構成図、責務表、異常系、判断事項。確認は正常系だけでなく外部依存停止・部分失敗を含める。

### L07 k8sの問題を絞る / 中級〜上級

> 対象cluster/context/namespaceと権限を確認し、まず読取専用の証拠で問題を絞ってください。機密を含むSecretの取得やログ全文の収集を避け、必要な状態・イベント・設定差分だけ確認してください。変更案には影響対象、復旧方法、確認手順を付け、本番変更や権限拡大は承認を待ってください。

成果物：ローカルの隔離環境での失敗fixture、証拠と仮説、最小変更、復旧確認。現時点でfixtureと実測は未作成。
限界：実clusterでの動作をローカルfixtureの成功から保証しない。APIは教材で固定したk8s版の一次資料で確認する。

### L08 低レイヤーの境界を守る / 超上級

> 正本から対象OS・カーネル・ABI・所有と寿命・資源上限・観測／制御の境界を確認してください。ホストや管理接続を対象外にした隔離実験を設計し、通常終了・部分起動失敗・強制終了・容量超過時の挙動を定義してください。静的ガードと実環境の検証を分け、特権操作の対象と復旧方法を示して承認を待ってください。ログから取得・送信の証拠以上の安全性を主張しないでください。

成果物：境界と異常系の確認表、隔離環境、ABI検査、復帰の証拠。初級者へ実行だけ勧める教材にしない。

veil-decoyのREADMEには検知を「100%確定的な侵害証拠」とする表現がある。教材ではトークンへのアクセスと侵害の確定を同一視せず、検証・自動スキャン等の別の説明可能性を扱う。今回その検知精度は確認していない。
両題材は公開前にcommit固定、必要ファイルの確認、ライセンス／第三者帰属、公開証拠の確認、再現手順の整理を行う。既存の非公開ログや個人PCの成果物を自動取り込みしない。

## 7. 更新を必須にする運用

更新の仕組みを初期範囲に含める。通信や利用者への毎回評価は強制しない。
教材リリースには担当、確認日、対象環境、根拠、次の見直し条件を必須にし、欠落したものは公開可能な「検証済み」にしない。
見直しトリガー：対象ツール／モデルの変更、出典の変更、再現失敗、具体的な逸脱報告、設定した再確認期日。
確認期日は領域の変化とリスクに応じて編集者が設定し、根拠なく全教材に同じ短期更新を要求しない。
旧版は閲覧・Export可能。鮮度の問題は表示し、理由なく通常の利用を全面停止しない。

変更案 → schema／リンク／fixture検証 → 教材レビュー → リリースパック → 利用者の差分確認 → 導入、を必須経路にする。
新しい組み込み版の導入と、既存プロジェクトの版更新は別操作。派生レシピは元版・自分の版・新版の比較を出し、黙って上書きしない。
利用者が保存した版は、採用するまで固定する。強制的な最新版への切替で昨日の依頼の意味を変えない。
メンテナンス担当が不在なら「更新停止／最終検証日」を表示する。アプリなしでも教材を読み使えるExportを維持する。

## 8. フィードバックの改善判断

原因候補：指示の曖昧さ、入力不足、環境能力の不足、モデルの不遵守、正本との矛盾、検証不足、不明。
修正は追加だけでなく、削除・短縮・条件付け・別レシピへの分割・非推奨を選べる。
成功報告でも不要な指示を減らせるかを考える。修正案は報告と根拠に紐付け、採用前後の版で同じ課題を再確認する。
共有は任意で、利用者が内容・送信先を確認する。案件メモ、回答、ログは既定で共有しない。
フィードバックをAIモデルの訓練に使う機能は本設計に含めない。

## 9. 公開教材の品質基準

- 学習目標に対応する実例と、入力・成果物・確認方法がある。
- 適用条件と利用不能な操作が分かり、失敗・停止・復旧を扱う。
- 出典と確認範囲、未検証事項、権利を明示する。
- 効果を掲げるなら比較条件と取得できた結果を添える。
- 新しい会話・別環境で、個人の長い履歴なしに使えるか確認する。
- 説明を読んだ利用者が、自分の課題への適用理由を説明できるか任意の利用観察で確かめる。

長さ・教材数・高難度・AIの同意を品質基準にしない。公開判断は人が行う。

## 現行教材と改善の境界（2026-10-08）

カタログは元の8本の教材の分類付きv2と、恒久修正・リファクタ・全体分析・アーキテクチャ比較・ディスカッションの5本、計13本。元のv1は不変のまま保持し、既存の割当を差し替えない。教材と個人台帳は表示を分ける。個人登録には教材の全項目を要求しない。

版に紐付く任意フィードバック、変更理由を伴う新版、旧版参照、手動Importの確認は実装済み。フィードバックから改善案への自動対応、差分採用、定期的な一次情報取得、教材の性能比較は未実装。AIガイドは2026-10-04の同梱スナップショットであり、実行時に最新情報を取得した表示にしない。

現行の例は確認手順と限界を学ぶ候補。実案件の改善率、トークン節約、初級から超上級までの再現実験はまだ証拠がない。veil等の素材を検証済み教材と呼ぶには、対象commitと権利、隔離fixture、再現結果を揃える。
